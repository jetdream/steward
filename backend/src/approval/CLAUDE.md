# backend/src/approval/ — Ready / Approvals (ARC-17 / APR)

**Purpose.** The disposition surface of the weekly visit (XH-1) — the Ready spine
and the two founder verbs (approve / redirect) plus the manual composer. It takes
VAL-cleared drafts from the content engine (GENS via PIPE-2) and records founder
verdicts before publishing (PUB). Implements the behaviour spec **APRS**
(`.spec/specs/apr-approval-inbox.yaml`).

| File | Role | Spec |
|---|---|---|
| `dispositions.ts` | the pure `batchEligible` filter (the load-bearing batch-exclusion invariant) | `@implements APRS-1` |
| `index.ts` | `createApproval` facade — readyStack / approve / batchApprove / editDraft / skip / redirect / proposeRule / compose | `@implements APRS-1/3/5` |

**No new spine entity (DM-5).** The Ready stack is an ORDERED VIEW over pending
ContentItems (draft / awaiting_picture), with the OPSS-1 QA gate withholding
`qaStatus = pending-review` drafts. Each card carries its per-channel variants
with their GENS-5 fit verdicts (XH-5). The ONE new table is the **edit-diff log**
(`@shared/db/edit-diff.ts`) — a deferred part of the DM-5 aggregate, not a new
top-level entity.

**Deterministic dispositions (LRN-20).** Every disposition is routing/state/policy,
never a content judgment:
- **approve** — draft → approved, GATED by `canApprove` (GENS-3/4: no picture ⇒
  blocked, `awaiting_picture`). At TL0 approval is per card (AUT-1).
- **batchApprove** — approves the ready cards where `batchEligible` holds; NEVER
  clears a held (GR-3/GR-8 escalated), awaiting-picture (GENS-4), or non-draft
  card — the One-Home invariant (DEC-18).
- **editDraft** — updates the master/variant body + appends an `edit_diff` row
  (the APRS-3 learning-loop data).
- **skip** — draft → skipped; an optional after-the-fact reason writes Memory
  (CHTS-5 enrichment).

**The learning loop writes ONE way (MEMS-1).** skip-reason, redirect (CHT-2
confirm-back — the confirm happens client-side, this binds), and an accepted
rule-proposal all go through `memory.write(..., { correctionChannel: true })` →
a styleRule/taboo, never a bare fact. The Strategy §c view projects them (DEC-22).

**The composer is not a bypass (APRS-5 / LRN-22).** `compose` runs the founder
master through the SAME chain a planner slot takes: the VAL guardrail judge
(`port.checkGuardrails` — held/flagged exactly like generated content), then
`persistDraft` (lands `awaiting_picture` without a picture — GENS-3/4), then
`adaptContentItem` (GENS-2 per-channel + the GENS-5 fit gate). No APR-side pipeline,
no direct-publish side channel.

**Deferred (documented keyed follow-on).**
- **APRS-3 recurring-edit-PATTERN detection** — the LLM/statistical judgment over
  the accumulated `edit_diff` log that SURFACES a rule-proposal card ("you've
  shortened 4 X posts in a row — set 'max 200 on X'?"). The loop's data capture
  (editDraft → edit_diff) and its founder-confirmed write (proposeRule → Memory)
  are here; the detector that proposes from the diffs is a later Skill + eval.
- **Bare-approval reinforcement** (MEMS-1) needs the draft→grounding provenance
  link (which retrieveContext set produced the draft) — a follow-on.
- **AUT-1 TL1** auto-approve + veto-window (P2), **APRS-4** notifications (Email
  port IG-5), **APRS-2** cadence, **APR-6** quiet accountability (P1).
